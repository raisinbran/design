# Optional Companion Integration

`CompanionService` uses a private, versioned loopback channel. Each app has a separate Electron single-instance lock (`Portfolio Tools/{appId}` user data), and a random 256-bit bearer token in a mode-0600 endpoint file. The service binds only `127.0.0.1`; credentials are absent from URLs, command arguments, renderer state, and website content. This boundary trusts the current OS account, not other software running as that same account.

Studio Settings explicitly locates an installed executable or macOS `.app` and enables/disables linking. App launch uses `spawn` arguments without a shell; macOS bundles use `/usr/bin/open -a`. An existing independently running Processor can receive a task. Failed linking explains how to open Processor independently. Neither app requires the other to start.

The shared UI controls are isolated in `src/renderer/companion-controls.tsx`. Studio uses `CompanionSettingsControl` and `CompanionLaunchControl`; Processor displays `CompanionTaskBanner`. Narrow preload methods/events are in `contracts.ts`. Processor can retrieve missed startup tasks with `getCompanionTasks()` and a saved source/recipe with `getCompanionSource(taskId)`. The latter exposes an opaque source handle, not the original path. Missing sources return `needsRelink: true`.

## Publication Handoff for Steps 5 and 7

- `PrivateSourceStore` reads/writes private `PrivatePhotoSource` records under the shared private directory, keyed by workspace hash and photo-key hash. Reframing must always restart from this original and recipe. Relink through an explicit native file chooser when missing.
- `WorkspaceWriter.run(workspaceId, expectedRevision, save)` acquires the same exclusive private lock for both apps and rechecks the catalog revision before calling the save operation. Step 7 must put the full transaction inside this callback and also check individual destination-file digests, including generated website consumers and image outputs.
- A crashed writer deliberately leaves its lock. Step 7 must offer explicit recovery after proving the recorded owner process is gone, then reconcile its private journal/backups before releasing that stale lock. Do not silently remove a live lock.
- After a durable publication commit, main-process processing code calls `services.companion.recordPublication(taskId, photoKey, revision)`, then `services.companion.complete(taskId)`. Reframe receipts must match the task's photo identity. Renderer IPC cannot create a publication receipt. Completion refuses a bare unrelated catalog change.
- Notification failure after publication (for example Studio closed) must not roll back a successful publication. Keep the outcome clear and allow Studio's manual refresh; the next app can select/read the same catalog independently.
- Companion completion refreshes Studio through `onWorkspaceChanged`. Step 4 must preserve unsaved management edits on this event by offering reconciliation instead of replacing dirty editor state.

Tests cover auth/version rejection, optional enablement, real private HTTP delivery, renderer privacy, receipt-gated completion, concurrent writers, and external changes. This managed environment needs network permission to listen on loopback during the integration test; normal installed applications use the operating system's local networking directly.

## Processing Handoff After Step 5

`ProcessingService` owns exact encoded bytes in a bounded private memory cache. `renderPreview(sourceId, recipe)` returns an opaque token and actual encoded data URL. `publication(token, sourceId, recipe)` returns `PreparedPublication` only after matching the source/recipe and rechecking the original SHA-256. Step 7 must use those bytes directly, never re-encode the preview, write a clean intermediate, or create a full-size companion export. The prepared record contains the private original path and recipe for `PrivateSourceStore.write`; none of those private fields belong in public JSON or generated JS. `discard(token)` releases bytes after successful publication. Cache eviction requires a fresh render.

The Processor queue retains `preview` and `renderedRecipe` per original. Changing recipes hides stale previews immediately, and a render that finishes against a changed recipe/workspace is rejected by the UI. Step 7 must also enforce the main-process `publication` check. The primary Add action remains disabled until the transaction service wires it. Rendering queue previews is sequential, shows actual worker stages, supports cancellation, and leaves errors attached to the source.

`saveProcessingDraft` and `getProcessingDrafts` persist/resume private original references and recipes outside the website. Missing originals require explicit relinking. Recovery UI can resume drafts; Step 7 adds interrupted public transaction recovery beside it. `getProcessingDefaults`/`setProcessingDefaults` persist the full recipe privately. A fresh framing task uses the original recipe through the existing source store, never the watermarked publication.

The worker imports `heic-decode` and bundled `libheif-js` from each app's own production dependencies. A synthetic real HEVC/HEIF fixture proves decoding, and the packaged Linux Processor worker decoded that fixture successfully from `app.asar`. Both compiled app workers also decoded libheif's larger public example (800 × 534 output). macOS/Windows codec installation checks remain part of native acceptance. AVIF brands bypass the HEIC fallback. `render-image.ts` has the protection hook for Step 6 to refine watermark design and verify metadata across formats.

Optional companion server startup failure now leaves each app usable independently; Studio linking then reports the unavailable service explicitly.

## Protection Verification After Step 6

`processing/protection.ts` renders tiled and corner masks at the final Published Image dimensions. Both use `watermark.strength` (default 0.16), normalized to the existing defaults. Tiled adaptive grayscale ink starts at 6/255 rather than the Python treatment's 7/255, a 14% base reduction. Highlight softening, texture lift, opposing detail edges, and an adaptive corner signature preserve visibility without white lettering dominating smooth dark areas. Long corner inscriptions scale to fit. Exact appearance varies with font rasterization and image detail; the slider and actual encoded preview remain the review controls.

Review compared original, legacy Python, and Electron outputs at 800 × 534 using bright/dark gradients, a detailed synthetic pattern, and bright/dark/unmodified versions of libheif's public example photograph. Temporary contact sheets are `/tmp/portfolio-protection-qa/contact-sheet.png` and `/tmp/portfolio-protection-qa/photos-comparison.png`. Sky and smooth shadows remained subtle; detailed backgrounds retained lettering. These are review artifacts, not public website files or bundled source photographs.

Every newly encoded WebP, JPEG, and PNG includes fresh EXIF Artist, XPAuthor (UTF-16), Copyright, and UserComment plus standard XMP Dublin Core creator/rights, xmpRights usage terms, and the IPTC/PLUS `DMI-PROHIBITED-AIMLTRAINING` property. The existing Python notice wording is unchanged. No legacy binary IPTC block existed to preserve; the existing applicable PLUS field remains in XMP across all three formats. Source GPS, capture dates, owner strings, paths, and source XMP are discarded by rasterizing before creating this allowlisted metadata. TIFF field parsing in protection tests independently verifies the actual encoded fields rather than only checking writer arguments.

Notices communicate restrictions; they do not technically prevent AI training. No adversarial pixel feature or signed provenance claim is implemented. Reprocessing still reads the original and saved recipe and never uses the already-watermarked publication. Tests confirm deterministic repeated output, immutable source bytes, separate tile/corner effects, shared-strength response, escaping, metadata privacy, and rights in all output formats. Updated packaged Linux Processor worker again decoded the real HEIC fixture and embedded XPAuthor and PLUS notices successfully. macOS/Windows native acceptance remains outstanding.

## Publication and Local Save After Step 7

`PublicationService` connects the real Save Locally and Add to Photo Catalog actions. Studio validates the complete draft and materializes changed catalogs, Photography JavaScript, Engineering sections, Archive sections, and Archive prominence settings together. Unedited records retain extension fields; unchanged Engineering templates and outside-page bytes are preserved. Archive source snapshots and hashes refresh after saves. The existing checkout's CRLF catalog templates are accepted against LF page files only when their normalized text is identical. The source hash still verifies the stored template. Edited rich text is checked for active content in the main process; source templates cannot be replaced through record extensions. Relative assets must exist and cannot traverse symlinks.

`Transactions` writes private before/after backups and a durable journal before installation. Both apps acquire `WorkspaceWriter` and recheck catalog plus generated-page revisions; destination hashes are checked before each replacement. Public staging files contain only the final protected output or authored website content. Private source/recipe records participate in the same recoverable transaction. A source original is never an output destination. A successful publication consumes the exact render bytes, then emits the companion publication receipt. Notification failure does not undo a successful local save.

Conflicting imports use a native Skip / Rename / Overwrite choice. Rename chooses an unused cross-platform basename. Reframing preserves the stable photo identity and management metadata. Format changes remove a prior sole Published Image only within the backed-up transaction and only when it is neither a saved/active original nor referenced by another public source file. Legacy paired full-size images are retained for reviewed migration. Web readers use the thumbnail for both legacy paired and single-image entries; malformed single-image entries never fall back to a full-size path. Python catalog validation supports the marker, and canonical floating ratios keep generated JavaScript identical after JSON round trips.

Settings in both apps, plus Processor Recovery, offer transaction review/restore and explicit stale-lock recovery. Recovery proves the old owner is gone, takes a separate exclusive recovery claim, verifies backups, and refuses unrelated external changes. Simultaneous recovery attempts cannot remove another recovery's new writer lock. A hard crash during the recovery operation itself can leave its private `.recovery` claim; that conservative refusal requires private-state review rather than automatically deleting a potentially live recovery claim. Completed transaction backups can also restore deliberate legacy cleanup while the saved destination hashes still match.

Studio offers three-way reconciliation of independent local and remote edits. Conflicting edits to the same field or order are refused and staged state remains available for manual resolution. The user reviews the merged draft before saving. Local website previews use a scoped loopback server and a sandboxed preview window without filesystem IPC; decoded traversal, private application folders, and symlinks are rejected.

Legacy migration begins with Identify Legacy References. It scans public source text for references and checks every saved original across shared workspaces plus active imported originals. Migration marks the selected existing thumbnails as sole Published Images while retaining full-size files. Cleanup is a separate confirmed operation, enabled only after references and source uses are resolved, and keeps private recovery backups. No migration or cleanup runs automatically. GitHub Desktop remains the commit-and-push step.
